Thin ai — Research Notes

A plain-language log of what's been built, what works, what doesn't, and what's next.

Last updated: May 2026

What ThinAI Is

ThinAI is a system that learns to play arbitrary turn-based games from a natural-language description of the rules. It runs entirely on a single laptop — no cloud APIs, no pre-trained models, no GPU clusters. The system parses game rules into a structured format, generates evaluation features automatically, and learns through self-play.

The core question: can classical AI techniques (search, evaluation learning, structured representation) match or exceed what neural approaches do for game learning — at a fraction of the compute?

Architecture

  • Natural language parser — converts plain English game descriptions into a Game Description Language (GDL) JSON format
  • Game engine — loads any GDL spec and handles legal moves, state transitions, and win/draw detection
  • Auto-feature discovery — analyzes GDL structure to generate evaluation features without game-specific knowledge
  • Auto-priors ("intuition") — derives initial weight biases from rule structure (e.g., "line-based wins suggest lines matter")
  • Minimax search with alpha-beta pruning — looks ahead N moves using learned evaluation weights
  • Sampling-based search — for card games with hidden information, samples possible opponent hands
  • Adaptive effort allocation — adjusts search depth per position based on branching factor and node budget
  • Self-play training — learns feature weights through win/loss reinforcement over ~40 games

What Works Well

  • Board games: The system consistently learns to play Connect Four, Reversi, Checkers, and Mancala at a reasonable level within 40 training games. It blocks threats, controls key positions, and improves over time.
  • Novel game parsing: The end-to-end loop works — paste a plain English description like "5x5 grid, 4 in a row wins" and the system parses it, generates features, trains, and lets you play. No game-specific code needed.
  • Auto-features: The system can generate reasonable evaluation features from the GDL structure alone, without hand-crafted knowledge. This is key for novel games.
  • Speed: Training 40 games takes 10-60 seconds on a laptop. Playing a move takes under 1 second. No GPU needed.
  • Card infrastructure: 7 card games work with hidden hands, melds, action cards, and multi-phase turns.

What Needs Work

  • Card game training: Card games with high luck variance (Go Fish especially) show noisy training curves. The learner and opponent share features, creating a ceiling around 50%. Better opponent selection or more training games may help.
  • Belief-state reasoning: The sampling-based search is implemented but its impact on play quality is not yet measured. The AI doesn't yet track what the opponent's plays reveal about their hand.
  • Opponent modeling: The opponent model infrastructure exists but isn't actively used during play. Integrating it with the sampling reasoner could improve card game performance.
  • Novel card games: The parser can describe card games but the engine can't execute arbitrary card game rules from parsed descriptions yet. Only grid-based novel games work end-to-end.
  • Search depth vs evaluation quality: The system currently relies on depth 4-5 search to play competently. A smarter evaluation function could achieve the same quality at depth 2-3, matching how humans actually think.

Estimated coverage of popular games

Of the ~50 most commonly played tabletop/card games worldwide, ThinAI's current architecture can represent roughly 60-70% with its existing game types (grid placement, card matching, shedding, collecting, comparing, movement). Adding trick-taking and territory mechanics would push this to ~80%. The remaining 20% require auction/bidding, real-time elements, or complex partnership dynamics that are outside the current scope.

The natural language parser can already handle novel grid-based games end-to-end. Extending it to fully support card game descriptions from English is a near-term goal.

Technical Decisions

Why not neural networks?

Neural approaches (AlphaZero, MuZero) need millions of training games and significant compute per game. They learn one game at a time and don't transfer. ThinAI's structured approach learns from rules, not just from playing, and transfers features across games via the GDL abstraction. The tradeoff: less raw playing strength, but vastly more sample-efficient and interpretable.

Why minimax instead of MCTS?

Minimax with alpha-beta pruning is simpler, more predictable, and works well with learned evaluation functions. MCTS would be better for very high branching factor games (Go), but none of our current games require it. The evaluation function is the learning target — depth is just how far ahead we look.

Why JSON for GDL?

Machine-parseable, human-readable, and web-friendly. The parser converts English to JSON, the engine loads JSON, the frontend displays JSON. One format throughout. The tradeoff: JSON can't express truly arbitrary game logic — complex conditions need built-in functions.
